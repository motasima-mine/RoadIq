# Documentation Steering Rules

## Purpose
These rules govern how Kiro generates documentation for the RoadIQ project. The goal is documentation useful to both engineers AND non-technical stakeholders (PMs, business analysts, operations teams).

## Audience
Write for two audiences simultaneously:
- **Primary:** Engineers integrating with or maintaining the app
- **Secondary:** PMs and business stakeholders who need to understand what the system does without reading code

## Required Sections for Every Document

### 1. Plain-Language Summary (REQUIRED — write this first)
- 2–4 sentences max
- Explain what this file/module does in business terms
- No jargon, no acronyms without explanation

### 2. What It Does
- Bullet list of capabilities, written as user-facing actions
- Start each bullet with a verb: "Calculates...", "Displays...", "Routes..."
- Avoid implementation details here

### 3. How to Use It
- Code examples for the most common use case
- Show realistic inputs and outputs where applicable
- Include error cases developers will actually hit

### 4. Inputs & Outputs
- Table format: field name | type | required | description
- Descriptions must explain the business meaning, not just the data type
- Flag fields with non-obvious behavior

### 5. Error Reference
- List error conditions and what they mean in plain English
- Include what the caller should do in each case

## Style Rules
- Use active voice
- Sentence case for headings (not Title Case)
- Code blocks must specify language for syntax highlighting
- Do NOT include internal implementation details
- Do NOT include TODOs or placeholder text

## File Naming
Output files should match the source: `app.py` → `app.md`, `drivers.json` → `drivers-data.md`

## Versioning
Include at the top of every generated file:
```
<!-- auto-generated by Kiro | source: {source_file} | updated: {timestamp} -->
```
